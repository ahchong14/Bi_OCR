# 评测集与回归检查:把「准不准」变成数字

## 它解决什么问题

以前判断准不准,只能看「人工改了多少」,而且每次改规则都是凭感觉。这里有两样东西:

1. **评测集(golden)**:每张收据 = 标准答案 + 模型当时的**原始回答**。存在 `eval/golden/golden.json`。
2. **回归检查**:用**当前代码**重放这些原始回答(不调模型,几秒钟),算出指标,和基线 `eval/baseline.json` 比。
   同一批输入上指标的任何变化都来自代码改动,所以变差就让 `bun test` 失败。

模型(Kaggle 上的 MiniCPM / GLM)又慢又不稳定,而门户自己的规则(字段整理、对账、分流、自动更正)是确定的,所以把两部分分开测。

## 日常用法(在 `receipt-portal` 目录下)

```powershell
bun run eval                       # 重放评测集,打印报告,对比基线;变差就退出码 1
bun run eval -- --mismatches       # 同时列出读错的收据
bun test                           # 回归检查已经在里面(server/tests/eval.test.ts)
```

改了识别或对账规则之后跑一下 `bun run eval`:
- 出现 `✗ 变差` → 这次改动让某个指标变差了,先别提交,看是哪一类收据。
- 出现 `✓ 变好` → 确认无误后记成新基线:`bun run eval -- --update-baseline --note "改了什么"`。
- 出现 `! 注意: 自动通过变少` → 规则收紧时的正常现象(这是有意的取舍),确认后更新基线。

## 用真实的 Kaggle 服务扩大评测集

先在**你自己的终端**里设环境变量(密钥只留在你的终端里,不要发给任何人):

```powershell
$env:MINICPM_URL = "https://xxxx.trycloudflare.com"
$env:MINICPM_KEY = "你的密钥"
$env:MINICPM2_URL = "https://xxxx.trycloudflare.com/m2"     # 可选:第二个读取模型
bun run eval:run -- --n 50          # 随机挑 50 张有标准答案的收据,调模型,存原始回答到 eval/runs/
bun run eval -- --runs eval/runs/run-xxxx.json --mismatches     # 看这一批的成绩
bun run eval -- --runs eval/runs/run-xxxx.json --promote        # 满意的话,加进评测集
bun run eval -- --update-baseline --note "加入 50 张"            # 样本数变了,重新记基线
```

- 不会碰门户的数据库,也不会写任何收据。只读图片、调识别服务、写一个 JSON。
- `--resume eval/runs/xxx.json` 可以接着跑;遇到密钥错误或限流会立刻停下,已跑完的都已保存。
- 默认跳过已在评测集里的收据,每次跑的都是新的;`--seed 2` 换一批。
- 速度大约和门户扫描一样(每张 15~20 秒);50 张约 15 分钟,200 张约 1 小时。

从门户里已经扫描过的收据直接导出:`bun run eval:export`(只读,先复制数据库再读;只导出有标准答案的)。

## 指标怎么读

| 指标 | 含义 | 看什么 |
|---|---|---|
| 总额 / 日期 / 商家 读对 | 机器原始结果和标准答案一致的比例(商家名相似度 ≥ 0.9) | 越高越好 |
| **错放** | 「基本可信」(自动通过)的收据里其实有错的比例 | **最重要,越低越好,底线是 0** |
| 拦截率 | 读错了的收据里,被交给人工的比例 | 应该是 100% |
| 误报 | 读对了的收据里,被多余拦下来的比例 | 决定要人工看多少,越低越好 |
| 每条提示准不准 | 某条原因代码出现的收据里,真的有错的比例 | 找该放宽或收紧的规则 |

## 要知道的限制

- **标准答案只有商家、日期、总额。** 税额、明细、付款没有标准答案,所以「读对了却被拦」里有一部分是对的:
  那张票的总额读对了,但税额或明细确实有问题。误报数字偏高,不全是规则的错。
- **样本越少,门槛越松的改动越测不出来。** 评测集 131 张(其中 100 张来自实机运行)。31 张时,三个修复看起来「0 错放」,
  到 131 张才暴露出商家名和日期的错放 —— 所以改规则后要看 131 张的结果,不要只看小样本。
- **标准答案本身有歧义的收据**(例如标准答案写营业地点名,票头印的是零售商),在 `server/tests/eval.test.ts` 的 `LABEL_AMBIGUOUS` 里登记,不算模型的错放。
- 原始文字里每段模型回答最多存了 2000 个字符,超长的明细会被截断(极少数很长的票)。
- 重放用的是当前代码对**当时模型输出**的处理。换了模型或提示词,要重新跑 `eval:run` 才反映真实变化。

## 审核更正 → 完整标签 → 商家记忆表

**完整标签。**SROIE 标准答案只有商家、日期、总额,商品、税额、小计、付款没有标准答案,所以那部分一直没有数字。
审核员逐张看过并通过的收据,最终值就是「人确认过的答案」:

```powershell
bun eval/export-reviewed.ts                                           # 只读数据库副本,写 eval/golden/reviewed.json
bun eval/report.ts --golden eval/golden/reviewed.json --mismatches    # 报告里多一节:小计 / 税额 / 实付 / 找零 / 商品
```

- 只导出「逐张审核通过」的(批量通过没有逐张看过,不算)。样本少于 30 张时数字只能参考。
- 税额、服务费这类字段,「模型凭空编了一个、而审核员确认票上没有」算读错 —— 这正是最常见的错。

**商家记忆表(`merchant_alias`)。**审核员逐张通过时,机器读到的商家和最终商家差得多(相似度 < 0.9)就记一条「读法 → 确认名」;
以后扫描到同一个读法(去符号后相同,出现过 1 次;或相似度 ≥ 0.92 且出现过 2 次)直接换成确认名,并且不再标「商家法定名不同」。
审核员确认过的商家名本身(已通过的收据)也不再被标「法定名不同」。

`bun eval/report.ts` 末尾的「学到商家别名之后(留一法)」模拟这个效果:评测每一张时,别名表只用别的收据建,不含自己和同一张票的另一次扫描。
没见过的店没有任何好处,所以不会高估;但评测集里重复出现的店比较多(SANYU 等),真实使用里的好处取决于你们供应商的重复程度。

标准答案来自 Hugging Face 的 `Voxel51/scanned_receipts`(SROIE 的整理版,CC BY 4.0),使用时需要署名。

## 第二意见(按需升级)的评估

门户可以只对第一轮「不是基本可信」的收据,在后台队列里让第二个读取模型(GLM-OCR)重读,Jev 给两份转写打分,Qwen3.5-4B 只看文字仲裁两边不一致的字段。

| 环境变量 | 作用 |
|---|---|
| `MINICPM2_URL` | 第二个读取模型地址(网关的 `/m2`)。不设就没有第二意见 |
| `SECOND_MODE` | `flagged`(默认,只对不确定的)/ `all`(每张都读)/ `off` |
| `QWEN_URL` / `QWEN_KEY` / `QWEN_MODEL` | 文字仲裁(网关的 `/qwen`)。不设就只比较两个模型的读数 |
| `SECOND_UPGRADE` | `1` = 允许自动升级成基本可信(升级前用采纳后的值重新校验)。**默认 0 = 影子模式**:只存储和显示 |
| `SECOND_CONCURRENCY` | 队列并发,默认 1 |

流程: 影子模式扫一批 → 等队列处理完 → 看成绩,确认「升级后和标准答案不符」为 0 再打开 `SECOND_UPGRADE=1`。

```powershell
bun eval/run-via-portal.ts --n 100                         # 门户(影子模式)扫一批,得到 eval/runs/portal-xxxx.json
bun eval/run-second.ts eval/runs/portal-xxxx.json          # 只读门户: 不一致时谁对 / Qwen 仲裁对不对 / 一致但都错 / 升级会不会错放
```

任何失败(第二个模型超时、Qwen 不可用、转写里找不到仲裁选的值)都只会让第二意见缺席或降级成「都不是」,不会影响这张收据本身。

## 混合读法(HYBRID_DETAIL)

商家 / 日期 / 币种 / 总额沿用 MiniCPM 原生读数;小计 / 税额 / 折扣 / 服务费 / 舍入 / 实付 / 找零 / 商品行改用 Qwen 从 MiniCPM 自己的整页转写里抽的值;总额或日期两个读者读得不一样 → 转人工(不放行)。

| 环境变量 | 作用 |
|---|---|
| `HYBRID_DETAIL=1` | 打开混合读法(默认 0)。**必须同时设 `QWEN_URL`**(和第二意见共用同一个 Qwen)。每张多一次 Qwen 调用约 5~6 秒;Qwen 不可用 / 超时 / 返回乱码时原样用原生读数,扫描照常 |

评测(`eval/qwen-extract.ts`,离线,已存转写 + Qwen 回答):

| | MiniCPM原生 | 混合+分歧转人工 |
|---|---|---|
| 随机 100 张: 自动通过 / 错放 | 66% / 4 | **75% / 4** |
| 难样本 50 张: 自动通过 / 错放 | 38% / 4 | **46% / 5**(多出的 1 张是商家标注粒度,不是读错) |
| 难样本 50 张: 小计 / 税额 / 实付 / 找零 / 商品行 | 40 / 66 / 86 / 84 / 80% | 70 / 94 / 100 / 98 / 92%(标准是助手审核值,仅参考) |

局限: 原生的规则是针对评测集调过的,所以对比偏向原生;明细字段只有 50 张可测,标准不是人工的。上线先小批量试,抽查带「detail_from_qwen」提示的收据。

```powershell
bun eval/make-subset.ts --n 100 --seed 5 eval/runs/<已用过的>.json                      # 从评测集挑一批(带 MiniCPM 转写)
bun eval/qwen-extract.ts eval/runs/qwen-golden100.json --source minicpm [--redo]        # 让 Qwen 抽(需要 MINICPM_URL / MINICPM_KEY,走 /qwen)
bun eval/qwen-extract.ts --score eval/runs/qwen-golden100.json                          # 不调模型,只重算成绩(含混合各列)
```
