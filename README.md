# 收据审核门户 / Receipt Review Portal

把识别流水线输出的收据数据,变成员工能直接用的网页:对照原图核对、修改、通过或驳回,所有操作留痕;已处理的数据可以查表格、做统计分析、导出 CSV。**界面支持中文和 English**(右上角 ⚙ 切换,也会自动跟随浏览器语言)。

**技术栈**:后端 [Elysia](https://elysiajs.com)(Bun 运行时)· 数据库 SQLite(`bun:sqlite`,WAL 模式)· 前端 TypeScript + React + Vite · 表格 TanStack Table · 图表 Recharts · 前后端共用类型(`shared/types.ts`)和对账算法(`shared/reconcile.ts`)。

## 快速开始

需要先安装 [Bun](https://bun.sh)。

```bash
bun install          # 安装依赖(只需一次)
bun run build        # 构建前端(改了前端代码后再运行一次)
bun run start        # 启动,打开 http://127.0.0.1:8080
```

让同一局域网的同事访问(必须设口令):`bun run start --host 0.0.0.0 --token 你的口令`。
环境变量:`PORT`、`HOST`、`PORTAL_TOKEN`、`PORTAL_DATA`(数据目录,默认 `./data`,里面是 `portal.db` 和 `images/`)。

## 门户内直接扫描(拖图片 → 识别 → 审核)

右上角「📷 扫描 / 导入」→ 把收据图片拖进去(可多选,也可以拖到页面任意位置)。服务器逐张识别(同时最多 2 张),识别完一张就进入「审核」队列,可以边扫边审;关掉窗口识别也继续,页头有进度,完成后有提示。

- **识别服务**:内置 OCR.space(有免费额度,图片会发送给第三方,界面上有提示和确认)。设置 `OCR_SPACE_KEY=你的密钥` 用自己的额度;不设则用公开共享的测试 key(随时可能被限流)。`PORTAL_SCAN=off` 完全关闭扫描。
- **字段提取**:`server/lib/extract.ts`(规则加正则,总额/付款/日期规则与 Kaggle 流水线一致),再用对账算法分流。读不准的字段留空;字段齐全且算术能互相印证才标「基本可信」,其余一律「需检查」(只有一个识别来源,不给最高档)。
- **大图**:超过识别服务上限(OCR.space 免费版 1MB)自动缩小后识别,原图原样保存。
- **省额度**:先按图片内容查重,扫过的不再调用识别服务。
- **失败处理**:识别不出文字也入库(留空待手填);限流会暂停并提示,可「继续扫描」;临时性错误自动重试。
- **换识别服务**:只依赖 `server/lib/ocr.ts` 里的 `OcrProvider` 接口。已有两个实现:OCR.space(默认)和 **MiniCPM-OCR**(见下一节)。
- **已知限制**(OCR.space 模式):商品明细基本提取不出来(会留空);准确率只核对过少量样本。

### 用 MiniCPM-OCR 识别(多模态模型直接读字段)

设置 `MINICPM_URL` 就改用它,不设就保持上面的 OCR.space。模型直接回答"商家、日期、金额是多少"和商品明细,不再走"先转文字再用规则猜"。服务端是任何 OpenAI 兼容接口的 llama-server / vLLM,可以在本机、内网 GPU 机器、NAS,或者(测试时)通过隧道指向 Kaggle(笔记本在 `../kaggle_receipt_ocr*.ipynb`,运行后会打印要设置的值)。

```powershell
$env:MINICPM_URL = "http://192.168.1.50:18499"     # 或 https://xxxx.trycloudflare.com
$env:MINICPM_KEY = "服务端 --api-key 设置的密钥"
bun run start
```

| 变量 | 说明 |
|---|---|
| `MINICPM_URL` | 服务地址。**不在本机/内网时必须是 https://**,地址里不能带账号密码;写错会直接拒绝启动(不会悄悄退回 OCR.space) |
| `MINICPM_KEY` | 服务端的访问密钥,以 `Authorization: Bearer` 发送。公网地址务必在服务端设 `--api-key` |
| `MINICPM_MODEL` | 模型名,默认 `minicpm-ocr`(服务端的 `--alias`) |
| `MINICPM_FULLTEXT` | **默认开**。多问一次整页文字:放进审核页的"识别出的原始文字",并用它交叉验证模型读出的金额和日期(见下)。多一次模型调用;设成 `0` 可关掉换速度,但没有交叉验证 |
| `MINICPM_TIMEOUT_MS` / `MINICPM_CONCURRENCY` | 单次提问超时(默认 180000);同时识别几张(默认 1,单卡单路的服务别调大) |

- **每张图问 3 次,再加一次整页转写(默认开,共 4 次)**:核心字段 / 附加字段 / 商品明细,字段分组问是因为一次问太多相近的字段(服务费、舍入、合计)小模型会串位。串位的结果会被对账算法抓到,标「需检查」。
- **分流用同一把尺子**:模型读出的字段和规则提取走同一个 `triage`(字段齐全 + 算术互相印证才标「基本可信」),**不会因为是模型读的就放宽**。日期日/月有歧义、商家名像乱码、总额公式对不上,一律转人工。
- **交叉验证(有整页转写时)**:模型读出的总额、小计、税额、实付、找零,每个都必须能在整页转写里找到,找不到就用门户已有的原因代码标出来(`total_not_in_text`、`tax_not_in_text`…),字段高亮;规则从转写里读到的总额和模型的不同(`total_conflicts_with_text_rule`),或者日期不同(`verifier_disagrees:date`),都不能是「基本可信」。这是为了防多模态模型"编造一个看似合理的数字"。无小数的币种(日元、印尼盾等)转写里没有 `.00`,自动跳过"金额在原文里"这一项。商家名只在明显不同时给一个"第二次读到"的建议,不单独算问题。注意:这里的"第二次读取"是**同一个模型的整页转写加规则**,不是独立的第二个模型,界面文案沿用了"第二个模型读到"。
- **自动更正模型常见的两类读错**(来自一次真实扫描的观察,9 张里 6 张服务费等于税额,另有小计和总额颠倒的):① **抄值**:问到收据上根本没有的字段(服务费、折扣)时,小模型会抄一个相邻的数字而不说"没有"。服务费/折扣如果和税额、小计、总额、实付、找零或舍入金额完全相同,而且整页转写里找不到带"服务费/折扣"标签的那一行,就当作抄来的清空。② **小计和总额颠倒**(含税合计被读成小计):只有在"实付 − 找零 = 小计,并且 总额 + 税 = 小计"同时成立时才调换,用付款信息作佐证。两种都会写入「更正记录」、原因代码 `auto_corrected:字段`,状态最高给「已更正」(不会是「基本可信」),审核页可以一键恢复原值。**没有付款佐证、或者转写里确实有该标签的行,一律不动。**
- **模型的反馈在门户里哪里看**:

| 内容 | 位置 |
|---|---|
| 各字段、商品明细 | 审核页表单(可修改,改动留痕) |
| 模型对每个提问的原始回答 + 整页转写 | 审核页「识别出的原始文字」,按 `[full text]` / `[core fields]` / `[extra fields]` / `[line items]` 分段,数字可点击填入金额格 |
| 各阶段耗时 | 审核页底部「识别信息」一行(核心 / 附加 / 明细 / 整页转写 / 总耗时);扫描窗口每张显示"N 项商品 · X 秒" |
| 这张是谁识别的 | 批次名里带识别服务名(`scan … · minicpm-ocr@主机`),审核页「识别信息」和「操作记录」都能看到 |
| 交叉验证结果 | 队列摘要、审核页提示条、字段高亮、"文字中读到 / 第二个模型读到"的一键采用建议 |
| 模型报错的真实原因 | 门户终端的 `[scan] 文件名 识别服务出错 …`(界面上只显示一句通用提示) |
- **隐私**:服务在本机/内网时界面不再提示"发送给第三方",也不要求勾选确认;在公网地址(如 Kaggle 隧道)时仍然提示,图片会经过隧道提供方和那台机器。
- **模型输出当作不可信文本**:只采用约定的字段名(多塞的键被丢弃),文字字段折叠换行并截断,日期/金额按门户统一规则解析,读不懂的留空。
- **注意**:Kaggle 的链接会话结束就失效,每次重开都要换 `MINICPM_URL` 和 `MINICPM_KEY`。接口约定(提示词、字段名)在 `server/lib/minicpm.ts` 和 `server/lib/structured.ts`;准确率需要用你自己的收据核对,**不要因为"基本可信"就跳过抽查**。

## 对照标准答案(直接衡量识别准不准)

以前判断准确率只能看「人工有没有改」,批量通过和审核员没发现的错误都不会算进去。现在可以导入一份标准答案,门户直接数「机器读对了几个」。

1. 「📷 扫描 / 导入」→「📋 标准答案」,导入 CSV:列 `file, company, date, total`(可选 `address`),`file` 要和收据的文件名一致,可重复导入(同名更新)。分析页的空卡片上也有「导入标准答案」按钮,会直接打开到这个页签。
2. 「分析」页的「对照标准答案」卡片,按**识别来源**分开,给出总额、日期、商家各读对了多少:大数字是**机器原始结果**与标准答案一致的比例(商家名相似度 ≥ 0.9 算对,与 Kaggle 脚本的 `score_against_label` 一致),小字是已审核通过的收据**人工确认后**的比例。样本少于 30 张标 ⚠ 仅供参考。
3. 下面列出读错的具体收据(机器读到什么、标准答案是什么、人工确认后对不对),点文件名直接打开那张。
4. 标准答案的日期按「日在前」解析(东南亚小票最常见);总额写法 `RM8.60`、`$7.60`、`1,234.50` 都能认。

示例数据:`../receipt data/Voxel51_labels.csv`(从 Hugging Face 的 `Voxel51/scanned_receipts` 整理出的 712 条,CC BY 4.0,使用时需要署名)。用它核对出的一个重要结论:OCR.space 模式下**总额读得很准,商家名是弱点**(见 `server/tests/extract-accuracy.test.ts` 里的 10 张回归样本)。

## 图上的文字框(点一下填字段)

识别服务给了文字位置时,审核页的收据图上会画出每个词的彩色框(工具栏的「框」按钮可以开关)。先点一个格子,再点图上的框:金额格子取框里的数字,商家格子取框里的文字,日期格子取框里的日期(`04/03/2018`、`22 MAR 2018` 都行,日在前)。点框和点右边「识别出的原始文字」里的数字效果一样,只是在图上直接对位置。

- **OCR.space** 会返回位置(扫描时自动请求并保存)。
- **MiniCPM-OCR** 直接读字段,不给位置,所以它识别的收据图上没有框,界面照常。
- 导入的 `receipts_result.json` 里每张收据可以带 `boxes`: `[{"t":"$7.60","x":0.8,"y":0.05,"w":0.16,"h":0.02}, ...]`,坐标是占整张图宽/高的比例(0..1)。卡号会按和原文一样的规则掩码。
- 数据库升到 v6(`receipt_blobs.boxes`),升级前自动备份 `portal.db.before-v6.bak`。

## 评测集与回归检查

`bun run eval` 用当前代码重放存下来的模型原始回答,对照标准答案算出总额/日期/商家读对了多少、自动通过的收据里有多少其实是错的(错放),并和基线比较,变差就失败。
`bun test` 里已经包含这项检查。用 Kaggle 上的模型扩大评测集的方法和指标含义见 [eval/README.md](eval/README.md)。

## 完整流程

1. 在 Kaggle 跑识别流水线(`../kaggle_receipt_workflow.py`),下载界面底部的 **portal_package.zip**。
2. 打开门户 → **导入收据**,把 zip 拖进去(重复的图片自动跳过)。
3. **审核**:左边队列按"最需要检查"排好;右边对照原图核对。
4. **数据**:所有收据的表格,可筛选、排序、勾选批量处理、导出 CSV。
5. **分析**:支出趋势、商家排行、系统识别准不准、系统提示是否可靠。
6. **操作记录**:谁、什么时候、对哪张收据做了什么,不可修改。

## 审核页:被标记的字段要确认才能通过

以前「需检查」的收据一次点击就能通过,系统标出来的字段只是摆在那里。现在:

- **被标记的字段要处理才能通过**:字段旁有「我核对过了」按钮,点它,或者直接改值(改过值本身就说明看过了),都算处理。还有没处理的就点「通过」,会弹出清单:可以「去核对」(自动滚动并聚焦到第一个没处理的字段,并闪一下),或者**写一句备注后「仍然通过」**(备注会记在操作记录里)。底部操作条有"⚠ N 项待确认",点一下跳到第一个。
- **哪些算"被标记"**:提示级别是「需检查」(warn)的,包括自动更正过的字段;只是说明性的(info)不算,「商品明细没读出来」也不算(门户扫描的收据几乎每张都有,逐张确认只会让人麻木)。
- **可以关掉**:右上角 ⚙ → 「通过前确认被标记的字段」→ 关,就回到以前的行为(只在金额对不上时才拦)。这个开关记在浏览器里,默认开。
- **提示条更好用**:按严重度排序(需要处理的在前);点提示条直接定位到对应字段;全部处理完的变淡;「只有一个识别来源」这句每张都有的话移到底部的「识别信息」里,不再占着最显眼的位置;干净的收据会显示"系统没有发现问题"。
- **自动更正看得清**:提示条直接写出改了什么(`总额: 6.23 → 6.60; 小计: 6.60 → 6.23`),金额统一两位小数;被清空的字段写"已清空"。每个被改的字段都有"恢复原值"按钮。
- **队列更好扫读**:每行显示"要看哪几个字段"的标签(日期、税额、总额…),没有具体字段时显示最多两行的文字摘要;数量为 0 的筛选置灰;选中的筛选处理完后自动回到「全部」(并且跳到下一张待审的,而不是停在刚通过的那张);排序下拉(最需要检查的在前 / 最新导入 / 最早导入 / 金额从大到小,记在浏览器里);队列顶部显示"本次已处理 N 张,还剩 M 张"的进度(这个浏览器标签页内计数,关掉就清零)。
- 手机宽度下队列区域本来就很窄,新增的排序行和进度文字会在窄屏上收起,只留一条细进度条。

### 审核页:键盘、姓名、佐证标记、按来源对比

- **键盘**:`J` / `K` 下一张 / 上一张;`F` 跳到第一个待确认的字段;`C` 把它标为「已核对」并跳到下一个;`R` 驳回;`?` 打开帮助。单键快捷键只在**没有在输入框里打字、也没有弹窗**时生效;在输入框里按 `Esc` 可以退出输入框。**故意没有单键「通过」**,避免误触,通过仍然用 `Ctrl+Enter`(同样会被"待确认字段"拦住)。没有做"通过后自动聚焦到下一张的字段":焦点一进输入框,`J` / `K` 就变成打字了,两者冲突。
- **姓名**:没填审核人就点通过 / 驳回 / 保存,直接弹出输入框,保存后自动接着完成刚才的操作(以前只弹一个提示,要自己去右上角找输入框)。
- **字段旁的小标记**(只在有整页转写时显示):金额(总额、小计、税额、实付、找零)在转写里也出现了 →「✓ 原文里找到了」;日期、商家与转写一致 →「✓ 与转写一致」。**只说明两次读到的一样、不是凭空编的,不代表一定对**;被任何提示标记过的字段不显示(比如日期的日/月顺序有歧义,字面一致解决不了歧义);无小数的币种(日元等)交叉验证本来就跳过,所以也不标;值被审核员改过就去掉。
- **原始文字**面板里,和表单当前金额相同的数字(带两位小数的)会高亮,一眼看出每个金额来自哪一行;整数(数量、百分比)不高亮。
- **分析页「按识别来源对比」**:来源取自批次名(门户扫描记录识别服务,隧道主机每次不同所以只取 `@` 前面;以前的扫描批次没记录来源;zip / json 是流水线导入)。同一套指标按来源分组:收据数、待审/通过/驳回、初判「基本可信」和「需检查」的占比、**人工改动率**(只统计逐张审核通过的,批量通过的不算;样本少于 30 张标 ⚠ 仅供参考)、**平均识别耗时**(只统计记录了耗时的收据,目前只有 MiniCPM 记录)。用来回答"换了识别服务之后,到底变好还是变差了"。

### 商品明细

- **有名字没金额**的行,金额格标成橙色并提示"缺金额";表格下面写出有几行没金额。
- **点原文里的数字填金额**:点一下某行的金额格,再点左侧"识别出的原始文字"里的数字,就填进这一行(以前只能填表头的金额格)。
- **明细合计**:表格下面实时显示各行金额相加,和上面的小计对比("✓ 和小计一致",或"小计 X,相差 Y"),不用再去看下面的对账提示猜哪里不对。
- **回车连续录入**:商品名 → 数量 → 金额 → 下一行的商品名;最后一行再按回车自动新开一行。表格下面也有"添加一行",行多时不用滚回表头。
- 没读到明细时不再只剩一个空表头,而是说明"明细不是必填"。

### 验证器 Jev(可选,免费)

MiniCPM-OCR-Jev 是一个 2B 的"判官"模型(权重 Apache-2.0,和 OCR 一样免费):给它 **图片 + 整页转写**,它打一个 0~1 的分,表示转写和图片是否一致。

**接法**:Kaggle 单单元笔记本里 `ENABLE_JEV = True`(已默认打开)。它会下载 Jev(约 3.8 GB)、装渲染环境(Chromium)、启动 Jev 引擎和官方的 render+score 服务,再起一个**带密钥的网关**:OCR 请求原样转发(行为不变),另有 `POST /jev/score`。门户仍然只认**同一个地址、同一个密钥**,多设一个开关即可:

```powershell
$env:MINICPM_URL = "<笔记本打印的地址>"
$env:MINICPM_KEY = "<笔记本打印的密钥>"
$env:MINICPM_JEV = "flagged"      # off(默认)/ flagged(只给初判不是「基本可信」的打分,省时间)/ all(每张都打,用来标定阈值)
bun run start
```

- **要求**:Jev 官方写明至少 12 GB 显存;Kaggle 请选 **GPU T4 x2**(Jev 放第二块 GPU)。只有一块卡时会和 OCR 抢显存,可能起不来。Jev 起不来不影响 OCR:网关不启动,隧道仍直连 OCR,门户日志会提示 `[jev] 打分失败`,扫描照常。
- **门户怎么用分数**:总是记录(审核页底部"识别信息"显示 `验证器 Jev 0.83(阈值 0.5)`)。低于阈值 → 加一条"验证器打分偏低"的提示,**默认不改状态**;分数从不会把一张收据变得更"可信"。`MINICPM_JEV_DEMOTE=1` 才会把「基本可信」降为「需检查」。验证器没打成分(超时、渲染失败)只记录原因,不当成收据有问题。
- **阈值 `MINICPM_JEV_THRESHOLD`(默认 0.5)只是占位**:官方不给通过线,而且官方评估的是文本/公式/表格区域,整张窄长收据不一定在它的训练分布里。先用 `MINICPM_JEV=all` 扫一批有标准答案的收据,看"读对的"和"读错的"分数分布,再决定阈值和要不要开降级。
- **没有在真实 Kaggle 上测过**:网关和门户这一侧有自动测试(假模型 + 真网关代码走完整条链路);Jev 引擎、渲染环境、官方 `/v1/rm/score` 接口那一段只按官方文档写成。首次运行请对照官方教程的 3 个样例自检(分数应与 `case.json` 里的 `observed_prob_yes` 相差 < 0.02)。
- **安全**:转写文字来自不可信的图片,会经 Markdown 渲染进 Chromium,所以网关先把 `< > &` 转义再交给 Jev;`/jev/score` 校验同一个 Bearer 密钥,限制请求体 32 MB、转写 2 万字符,Jev 一次只打一张。

## 对账算法(小计、税额等)

核心在 [shared/reconcile.ts](shared/reconcile.ts),流水线里有逻辑等价的 Python 版(`../kaggle_receipt_workflow.py`)。两个版本用**同一份测试用例** [shared/recon-cases.json](shared/recon-cases.json)(33 种真实可能出现的收据情形)约束,保证结论一致。

它处理的现实情况:

- **含税价与不含税价并存**:马来西亚 GST、英国/欧盟 VAT、日本内税(商品价已含税)与美国销售税(最后才加税)。算法在几种假设里找最吻合的,并告诉你判定的是哪一种。
- **折扣**:折扣可能已经体现在小计里,也可能在最后才扣,两种都试。
- **服务费、小费、外送/包装费**:都参与总额公式;税基是否包含服务费也会尝试。
- **现金舍入按币种**:MYR/SGD/AUD/CHF/CAD 0.05、NZD/HKD 0.1、JPY/SEK/NOK/INR 1、KRW 10、IDR 100;其他币种不允许舍入误差。舍入金额写明时只允许分位误差。
- **容差不随金额放大**:1000 元的小计差 3 块也是错(旧算法按 0.3% 会放过)。
- **付款核对**:实付 − 找零 = 总额,是独立于其他字段的最强校验;它和对账公式互相印证时,会建议更正总额。
- **缺字段时推算**:缺小计 → 商品合计;缺税额且差额正好是常见税率 → 建议税额;缺总额但有实付和找零 → 由它们推出。
- **商品行**:`price` 可能是单价也可能是行小计,两种都试;对不上时指出"去掉第 N 行就能对上"或"漏了约 X"。
- **税率合理性**:按含税/不含税分别计算;常见税率通过;美国/加拿大的地方税率、多税率混合只提示不报错;超过 30% 才警告。
- **常识检查**:总额为 0 或负数(退款)、折扣大于小计、某行金额超过总额、实付少于总额、舍入金额偏大。

## 对外 API(/v1,供 MCP 和其他系统调用)

独立于门户内部接口(`/api`),契约定义在 [shared/public.ts](shared/public.ts),带 `schema_version`(现为 `1.0`),以后只做向后兼容的加字段。口令用标准的 `Authorization: Bearer <口令>`(不需要门户专用的 `x-portal` 头)。

| 接口 | 作用 |
|---|---|
| `POST /v1/validate` | **同步对账**,不需要 GPU:传入金额、商品行、可选的 `taxes[]`(税率/税基/税额),返回含税/不含税判定、逐项检查、可采用的推算值、警告 |
| `GET /v1/receipts/:id` | 以公开契约返回一张收据(含对账结果、质量判定、人工复核状态);**不含** OCR 原文和图片路径 |
| `GET /v1/schema` | 契约版本,以及哪些字段是来自图片的不可信文本(商家名、商品名),下游模型不要把它们当指令 |

```bash
curl -X POST http://127.0.0.1:8080/v1/validate -H "content-type: application/json" \
  -d '{"currency":"MYR","subtotal":100,"tax":6,"total":106}'
```

**银行卡号**:导入时自动检测(13–19 位且通过 Luhn 校验)并遮盖成 `**** **** **** 1234`,原始卡号不落盘;发生过遮盖的收据会带 `card_number_masked` 提示。
**还没做**:提交识别任务(需要常驻 GPU 服务)、预签名上传、Webhook、MCP 适配层;详见 [docs/receipt-api-mcp-research.md](../docs/receipt-api-mcp-research.md) 的路线图。

## 安全说明

- 默认只监听本机;对外开放必须设口令(没设会拒绝启动)。
- 收据上的文字一律转义后显示,不会被当成网页代码执行;页面带严格的内容安全策略(CSP)。
- 写操作要求自定义请求头,防止别的网站伪造请求;只监听本机时校验 Host 头,防 DNS rebinding。
- 两个人同时改同一张收据时,后提交的会收到「已被他人修改」而不是悄悄覆盖(版本号乐观锁)。
- 导出的 CSV 会中和以 `=`、`+`、`-`、`@` 开头的文本,防止在 Excel 里被当成公式执行。

## 诚实说明:不要当成完整的生产系统

- **没有个人账号**:所有人共用一个口令,「审核人」是自己填的姓名,不能防冒名。需要真实身份请放到公司内网 + 反向代理(HTTPS、单点登录)后面。
- **没有 HTTPS**:口令和图片在网络上是明文传输,不要直接暴露到公网。
- 单进程 + SQLite,适合几个到几十个同时在线的审核员、几万张以内的收据。更大规模请换成正式数据库。
- 导入 zip 时整个压缩包会读入内存,默认上限 2GB;浏览器不能显示的图片格式(HEIC/TIFF)请在流水线打包时转成 JPG(流水线已自动处理)。
- 对账算法覆盖常见情形,但**不是万能的**:异常税制、多币种混合收据、分单付款等仍可能需要人工判断,所以它只给建议,不会自动改数据。
- 旧的 Python 版门户(`../receipt_portal`)数据库格式与本版不兼容,不会自动迁移。
